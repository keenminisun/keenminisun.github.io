핵심 판단: 가입/해지처럼 되돌리기 어려운 실행은 LLM 결과 하나에 맡기지 않는다. LLM은 고객 발화를 구조화하고, 경로/정책/실행/답변 사실은 코드가 결정하고 검증한다. LLM이 헷갈릴 수 있는 값은 규칙으로 막지 않고 입력에서 뺀다.

  • 고정 UI는 LLM 없이: 버튼/칩이 보내는 고정 문구는 UI 계약으로 보고 정확히 일치할 때만 fast path로 처리. LLM 호출 1회를 줄이면서 판정 흔들림도 제거

백엔드는 고객 발화를 다시 읽지 않는다

문제

LLM이 "도쿄"를 일본으로, "일주일"을 7일로 변환해도 백엔드 후처리가 "원문에 그 글자가 없다"며 값을 지웠습니다. 사용자는 이미 말한 국가와 기간을 반복해서 답해야 했습니다. 해석을 LLM에 맡겨 놓고 백엔드가 원문을 다시 해석하는 구조라, 표현이 늘어날 때마다 정규식과 단어 목록이 같이 늘어나고 결국 놓치는 경우가 생겼습니다.

개선

  • 판단에 필요한 근거를 LLM 출력 필드로 정의하고 백엔드는 구조화된 값만 읽도록 책임 경계 재정의
    • 요청 성격(실행/질문/문제 제기/진술): 질문형 발화("가입하면 얼마예요?")는 가입 흐름으로 들어가지 않음
    • 기간 연장, 변경 대상 필드, 일정 이동 일수, 상품 조건(종류/등급/요금제), 제외 상품
  • 동사 목록/어미 판정/도시→국가 사전 같은 원문 패턴 매칭 코드 제거
  • LLM이 틀리면 후처리를 덧붙이지 않음: 프롬프트에 대조 예시를 추가하고, 예시 JSON이 계약대로 파싱되는지 테스트로 고정하고, 실제 LLM E2E 케이스를 추가
  • 이 원칙을 팀 작업 원칙 문서로 정리해 계약/프롬프트/테스트를 같은 변경에서만 바꾸도록 함

운영 로그 분석에서 멀티턴 구조 재설계까지

1) 운영 로그를 원인 유형으로 분류

운영 검토 대상 로그를 원인 기준으로 12개 유형으로 분류했습니다.

  • 함께 쓰는 번호 입력 반복: 선택 입력인데 혼자 쓰는 고객이 본인 번호를 넣음 → 검증에 실패한 번호가 다시 띄운 폼에 그대로 채워져 같은 오류 반복. "번호 없이 진행"을 표현할 명령도 없었음
    • 조치: 실패 시 해당 slot 비우기, 사유를 먼저 말하는 오류 문구, [함께 쓰는 번호 없이 가입] 버튼, 계약에 빈 목록(= 번호 없이)을 명시적 값으로 추가
  • 되묻기 버튼 반복: 버튼이 처리할 수 없는 단어를 보내 누르면 같은 되묻기가 반복 → 버튼이 혼자서 해석되는 문장을 보내고, 버튼을 누른 턴이 또 되묻기면 고정 업무 메뉴로 전환
  • 진행 상태와 맞지 않는 응답: 진행 중 업무가 없는데 "해지할래"가 중단 안내로 끝남 → 확인/취소 같은 업무 전용 명령은 상태에 답할 대상이 있을 때만 처리
  • 히스토리가 현재 턴 사용자 발화 의도로 분류되어 잘못된 플로우 진입: 봇 응답에서 제안된 것/히스토리로 남은 정보가 다음 턴 의도분류에 영향을 주는 현상 다수 발생
    • LLM이 대화 이력에 남은 회선 선택 버튼 문구를 현재 조회할 번호로 추출
    • 봇의 틀린 답이 다시 이력에 저장돼 다음 턴의 입력이 되면서 같은 오류를 강화

분류 결과, 개별 패치로는 끝나지 않는 반복 유형이 이전 턴의 값이 현재 요청에 섞이는 멀티턴 오염이라고 판단했습니다.

2) 원인 분석

기존 형상처럼 코드단에서 추출 값이 현재 발화에 포함되어 있는지 regex로 검증하거나, 프롬프트에 금지 규칙을 더 추가하는 건 근본 해결이 아니라고 봤습니다. 멀티턴 오염 장애의 성격이 "더 구체적인 필드 규칙이 일반 금지 규칙을 이긴" 사례였기 때문입니다. LLM이 보면 안 되는 값은 규칙으로 막는 대신 아예 입력에서 빼야 한다는 판단을 했습니다.

3) 대화 원문 대신 구조화된 상태로 승계

LLM 입력을 현재 발화와 값이 없는 상태로 제한

  • 대화 원문, 상위 에이전트가 재작성한 질의, 이전 항목 값, 봇 문구를 모두 제거
  • 상태에는 진행 중인 업무, 대기 중인 질문, 채워진 항목의 이름만 둠 (값은 넣지 않음)

이전 값은 백엔드가 조건부로 승계

  • 백엔드가 저장한 최근 5턴의 구조화된 해석 결과에서만 값을 가져옴
  • 승계 규칙표: 방문지/기간/인원/상품을 그룹 단위로만 이어받고, 이번 턴에 값이 있으면 현재 값 우선. 규칙표에 없는 필드는 승계하지 않음
  • 명시적 참조: "그 상품", "거기", "같은 기간"은 LLM이 참조 표시만 하고 실제 값은 백엔드가 채움
  • 명시적 초기화: "기간은 아직 몰라"처럼 이전 값을 버리는 발화는 별도 필드로 표시
  • 되묻기/거절 턴은 저장하지 않음 ("오늘 서울 날씨 어때?" 다음 "로밍 추천해줘"에 서울이 붙지 않도록)

원문 히스토리가 하던 역할을 버튼과 상태로 대체

대화 원문을 빼면 "응", "두 번째 걸로", "베트남은?" 같은 발화는 직전 대화 없이는 해석할 수 없습니다. 이 의존을 끊기 위해 봇이 묻는 방식 자체를 바꿨습니다.

  • 확인/제안 질문은 버튼으로: 봇이 "~할까요?"라고 묻고 고객이 "응"이라고 답하면 직전 봇 문장이 있어야 의미가 생김 → 확인과 제안을 모두 버튼/칩으로 내고, 버튼은 그 자체로 해석되는 명령을 보냄. 고객의 선택이 자유 텍스트가 아닌 구조화된 이벤트로 이력에 남음
  • 봇이 보여 준 선택지: 상품 목록의 개수/라벨만 상태에 남기고, "두 번째 걸로"의 실제 값은 백엔드가 채움
  • 생략된 후속 질문: "베트남은?"에는 직전 턴에 실제로 답한 조회 종류만 상태로 전달

결과적으로 LLM은 이번 발화 하나와 값 없는 상태만 보고 의도/항목을 추출하고, 이전 턴과의 연결은 전부 백엔드의 구조화된 이력이 담당합니다. 이전 프로젝트 Weather Agent의 슬롯형 Entity 승계 설계를 했던 것을 기반으로, 로밍의 업무 흐름/확인/되묻기 단계를 상태로 옮기는 부분을 추가로 설계한 구조입니다.

운영 안정성

배포 중 스트리밍을 마무리하는 graceful shutdown

/talk은 응답을 먼저 돌려준 뒤 백그라운드에서 Event Hubs로 스트리밍하는데, 배포 신호(SIGTERM)에서 이 작업을 추적하지 않아 스트리밍이 로그 없이 끊겼습니다.

  • 백그라운드 작업을 레지스트리에 강한 참조로 보관하고(GC로 인한 유실 방지), 처리되지 않은 예외를 로그로 기록
  • FastAPI lifespan 종료 시 진행 중 작업을 20초간 drain하고, 초과하면 취소를 작업당 한 번만 전파. 두 번째 취소가 generator의 finally 정리를 중간에 끊는 문제를 막기 위함
  • 정리 중인 작업이 남아 있으면 공유 HTTP 세션을 닫지 않고 새 세션 생성만 차단
  • 시간 예산 설계: ACA 종료 유예(30초) > drain(20초) + 취소 확인(5초)으로 SIGKILL 전에 정리가 끝나도록 설정
  • 스트리밍 청크 발행 제한 시간(5초)과 종결 이벤트(60초)를 분리하고, Event Hubs 장애는 스트림 중단/실패 기록, payload 거부는 스트림 유지로 구분
  • 종료/취소 시나리오를 단위 테스트로 고정

Event Hubs 파티션 라우팅 고정

파티션을 Python hash(transaction_id)로 정했는데, 문자열 hash()는 프로세스마다 시드가 무작위라(PYTHONHASHSEED) 같은 트랜잭션도 워커/파드에 따라 다른 파티션으로 갈 수 있었습니다.

  • SHA-256 고정 해시로 바꿔 프로세스와 무관하게 같은 트랜잭션은 같은 파티션으로 전달
  • 파티션 수를 코드 상수가 아닌 배포 manifest와 같은 환경변수로 관리해 인프라 변경과 어긋나지 않게 함

측정과 재현 도구

  • 운영 로그 replay: 운영 요청의 여러 저장 형식(JSON/dict 표현/절단/이중 래핑)을 파싱하고, trace가 없으면 상태 이력으로 대화를 복원해 로컬에서 운영 장애를 재현
  • 턴 단위 관측: LLM 호출 수, 도구 호출, 상태 크기, 첫 발행 시각을 trace 필드로 기록하고 Application Insights 분석 스크립트로 집계
  • E2E 판정 보강: 문구뿐 아니라 업무 상태(흐름 시작 여부)와 LLM 출력 금지 필드까지 판정. 시스템 오류를 PASS로 세던 판정기 결함을 발견해 강제 FAIL로 수정
  • 형상 비교 도구: 여러 형상(커밋/모델/배포)을 같은 케이스로 병렬 실행해 턴 결과, 토큰, 소요 시간, 프롬프트 캐시율 비교. 전수 3,896턴 실행
    • 프롬프트 캐시 순서 변경(고정 카탈로그를 앞으로, 현재 시각을 user 메시지로)을 측정: 해석 단계 캐시율 94.2% → 94.8%, 답변 단계 62.1% → 62.3%. 효과가 작다는 것을 수치로 확인하고 후속 작업 우선순위 조정

v4 필드 하나에 책임 하나: 5개 독립 축, 단계별 타입 파이프라인, 정책 파일 분리 모호한 시각의 오전/오후를 LLM이 추론
v4.1 오전/오후 판단까지 백엔드로 이관 (sparse 출력 전환 중 LLM의 오전/오후 추론이 흔들려 책임을 덜어냄) — (현재 버전)

v0 → v2의 핵심: 조회 지역의 timezone은 외부 API 응답 이후에야 확정되는데, LLM은 그 이전에 날짜 계산을 끝내야 하는 구조였습니다. 현재 시각을 프롬프트에서 제거하고 발화 원형만 추출하게 바꾼 뒤, 오프셋 계산은 API 응답의 지역 tzOffset을 확인한 백엔드가 UTC timestamp로 수행하도록 옮겼습니다.

설계 전환의 계기: 시간별 요청이 시간 범위를 지운 문제

"mỗi tiếng"(매시간), "từng khung giờ"(시간대별) 같은 시간별 요청을 처리하려고 프롬프트에 규칙을 추가했습니다. 시간별 표현이 있으면 delta=5, relativeHours=0, 나머지 시간 필드는 null.

  • "từng khung giờ tối nay"(오늘 저녁 시간별) → 규칙이 "오늘 저녁"을 지우고 현재부터 5시간을 조회
  • 모델이 timeOfDay=eve를 살려도, 함께 나온 relativeHours=0이 resolver에서 우선돼 다시 현재부터 조회
  • 규칙을 빼면 "Đà Lạt mỗi tiếng"이 모든 필드 null로 추출돼 목록 응답이 단일 응답으로 바뀜

원인 분석: 우선순위를 더 세게 쓸 문제가 아니라 필드 설계의 문제였습니다.

  • delta 하나가 구간 길이, 목록/단일 응답 신호, 시간/일 단위의 세 책임을 동시에 가짐
  • delta=5가 "사용자가 말한 5시간"인지, "제품 기본값 5개"인지, "시간별 요청 표시"인지 구분 불가
  • timeOfDay도 이미 시작/종료/길이를 가진 구간인데, 시간별 규칙이 두 번째 구간을 만들어 구간끼리 충돌

검토한 대안: delta를 hourlyDelta/dailyDelta로 분리 → 단위 혼동은 사라지지만 구간 길이와 응답 단위가 겹치는 문제는 그대로 남아 기각

해결: 책임마다 필드를 하나씩 두는 Entity 단일 책임 원칙

  • 구간 길이 delta, 단위 deltaUnit, 기준점 관계 rangeRelation, 응답 단위 requestedGranularity로 분리
  • 시간별 요청은 응답 단위만 표시하고 구간을 만들거나 다른 필드를 지우지 않음
  • 사용자가 말하지 않은 기본값/sentinel(relativeHours=0으로 "지금"을 표현하는 등)은 entity에 넣지 않고, 기본 구간과 목록 여부는 백엔드 정책이 결정

v4: 다섯 개 의미 축

축 필드 질문
날짜 선택 specificDate/relativeDays/specificWeekday/weekPart (+ 수식어 relativeWeeks) 어느 날인가
하루 중 시점 specificHour/meridiem/timeOfDay/relativeHours 하루 중 언제인가
명시적 기간 delta(항상 양수)/deltaUnit(hour/day) 몇 개의 예보 지점인가
경계 관계 rangeRelation(from/after/to/before) 어느 방향이며 기준점을 포함하는가
응답 단위 requestedGranularity(hourly/daily) 시간별/일별로 나눠 달라고 했는가
  • 같은 축 안에서는 상호 배타, 다른 축끼리는 공존: "오늘 밤 시간별"은 relativeDays=0, timeOfDay=night, requestedGranularity=hourly 세 축이 모두 유지됨
  • "3일 뒤"(relativeDays=3, 한 시점)와 "앞으로 3일"(delta=3, after, 연속 구간)을 다른 필드로 추출
  • "며칠", "vài ngày" 같은 모호한 수량은 숫자로 변환하지 않음

경계 관계 = 방향 × 기준점 포함 여부의 2×2

관계 방향 기준점 예시
from 앞으로 포함 오늘부터 3일, 7시부터 4시간
after 앞으로 제외 7시 이후, 앞으로 3일
to 뒤로 포함 목요일까지
before 뒤로 제외 12월 25일 전 4일

v4.1: 오전/오후 판단도 백엔드로

"6 giờ đêm nay"(오늘 밤 6시)처럼 오전/오후 표시 없이 시간대 단어만 있는 시각에서 LLM의 meridiem 추론이 흔들렸습니다. 기존 규칙이 specificHour와 timeOfDay를 상호 배타로 정의해, LLM이 버려야 하는 시간대 단어를 근거로 오전/오후를 스스로 판단해야 하는 구조였습니다.

  • specificHour와 timeOfDay를 공존 가능하게 바꾸고, 시간대 단어가 있으면 숫자와 함께 그대로 추출
  • 명시적 표시("8 giờ tối", "7pm")가 없으면 LLM은 meridiem=null, 백엔드가 (시간대, 시각) 쌍으로 결정
  • 새벽/아침은 오전, 오후/저녁은 오후로 정책 파일에 선언하고, 자정/정오를 걸치는 밤/점심은 시각으로 판단 (밤 611시 → 오후, 밤 125시 → 오전)

단계별 타입으로 계산 책임 분리

RawTimeEntity → ForecastQueryPlan → CanonicalRange → ResolvedRange → PresentationPlan

단계마다 다른 타입을 반환하고, 앞 단계의 의미를 뒤 단계에서 다시 쓰지 않도록 설계했습니다.

단계 책임
RawTimeEntity: 입력 파싱 LLM 출력 타입/형식 검증, 실존 날짜 왕복 검증(2/30 등 불가능한 날짜 차단), 0과 미지정 구분, 의존 필드 정합성(deltaUnit은 delta가 있을 때만), 구버전 출력 하위 호환
ForecastQueryPlan: 의미 결정 공통 resolveByPriority로 정책 파일의 우선순위에 따라 날짜/시각/기간/응답 단위 선택, 결정 근거(source)를 trace에 기록
CanonicalRange: 범위 계산 조회 도시의 현지 timezone으로 자정을 넘는 시간대(밤 21~05시)/주 경계 계산, 현재 시각이 걸친 구간은 남은 부분만
ResolvedRange: 제공 범위 검증 전체 과거는 오류, 일부 과거는 현재부터로 자르고 안내, 끝만 한도 밖이면 한도까지 제공 (시간별 96지점/일별 15지점)
PresentationPlan: 표현 계획 응답과 카드의 유형/범위를 같은 계산 결과에서 생성, 카드 칸 수도 제공 한도로 제한
  • 시간 정책/제공 한도/카드 표현을 별도 정책 파일로 분리: "시간별 기본 5개 → 7개" 같은 기획 변경이 해석 로직 수정 없이 반영됨
  • 모든 결정에 source가 남아 잘못된 범위가 LLM Entity 추출 단계 문제인지 백엔드 계산 단계 문제인지 로그만으로 구분
  • 기존 약 500줄의 resolver를 단계별 모듈로 분리하고 테스트를 단계별 계약 테스트로 재작성

다국어 시간 표현을 공통 모델로 처리

  • 같은 tới(앞으로)가 단위에 따라 시작점이 다름: trong 3 ngày tới(앞으로 3일)는 내일부터 3일, trong 5 giờ tới(앞으로 5시간)는 지금부터 5시간
  • 언어별 문자열 예외 대신 단위의 의미 차이로 모델링: 날짜는 이산적인 calendar block, 시간은 연속적인 rolling window
  • 시점 오프셋(10 giờ nữa = 10시간 뒤 한 시점)과 기간(10 giờ tới = 앞으로 10시간)을 별도 필드로 분리
  • 성조 없이 입력된 베트남어(toi, sap toi)는 시간 범위 표현 안에서만 미래 표시로 인정

멀티턴과 지역 정규화

  • 이전 질문의 지역/시간/지표를 최신 턴부터 역순 탐색하되, 시간 값은 필드가 아닌 블록 단위로 승계해 서로 다른 턴의 시간 표현이 섞이지 않게 함
  • "다음 주 날씨 어때?" → "월요일은?"은 다음 주 월요일로 결합하되, 현재 턴에 다른 날짜 표현이 있으면 결합하지 않음
  • 지표는 미지정일 때만 이어받고 all은 명시적 초기화로 처리 ("비 와?" → "그럼 날씨는?"에서 강수 지표가 남지 않도록)
  • entity 추출 입력에서 대화 히스토리를 제거하고 멀티턴은 백엔드 승계가 전담 (이 구조가 추후 설계한 로밍 에이전트 멀티턴 격리의 기반이 됨)
  • 검색용 영문 지명(Ho Chi Minh City)과 표시/음성용 현지어 지명(Hồ Chí Minh)을 분리하고, 외국 도시는 음차하지 않음. 인식하지 못한 지명은 추측/교정하지 않음

값이 있는 필드만 출력하는 Sparse JSON

entity 추출은 매 요청의 핵심 경로에서 LLM 호출 1건당 평균 3.8초로 E2E 지연의 가장 큰 비중이었고, input token은 프롬프트 안정성 테스트 결과 더 줄이기 힘든 구조였습니다. 19개 필드 중 평균 14개가 null인 것을 로그를 통해 분석한 후, output token 및 시간을 줄이기로 결정했습니다. 값이 있는 필드만 출력하고 백엔드는 "키 없음 = 미지정"으로 해석하도록 바꿔 기존 기본값/검증 로직을 그대로 재사용했습니다. relativeDays=0처럼 유효한 0이 누락되지 않도록 규칙을 명시했습니다. Sparse JSON으로 변경하는 과정에서, 오전/오후 추출 품질이 흔들리는 것을 발견하고 백엔드로 이관하는 작업을 선행했습니다.

사용자가 나간 요청의 하위 작업까지 연쇄 취소

문제: 사용자가 답변을 받기 전에 나가도 LangGraph 실행, LLM 스트리밍, Knowledge API 호출이 끝까지 진행됐고, 전달되지 않은 질문/답변이 멀티턴 이력에 저장돼 다음 대화에 섞였습니다. 아무도 받지 않는 응답에 토큰과 커넥션도 소모됐습니다.

설계: 연결 종료 신호 하나를 요청의 전체 호출 체인에 전파

  • SSE 응답의 close 이벤트를 요청 단위 AbortController에 연결하는 핸들 구현 (signal/isCancelled/cleanup)
  • 응답을 다 쓴 뒤의 정상 close(writableEnded)는 취소로 보지 않도록 가드
  • 같은 signal을 graph.invoke, 공통 모델 호출부, Knowledge API 스트림까지 전달해 개별 에이전트 코드 수정 없이 모든 LLM 호출에 적용
  • 어댑터별 취소 방식에 맞춰 연결: GPT는 SDK signal, Gemini는 config.abortSignal, Gemma는 fetch의 signal

타임아웃과 사용자 취소의 구분

  • 어댑터 자체 타임아웃 signal과 클라이언트 signal을 AbortSignal.any로 합쳐 먼저 오는 쪽으로 중단
  • 둘 다 AbortError로 올라오므로 클라이언트 signal의 aborted 여부로 원인을 판별
  • 사용자 취소는 cancelled 코드/info 로그, 타임아웃은 timeout 코드/warn 로그로 분리해 사용자 이탈이 LLM 장애 지표로 집계되지 않게 함

끊긴 턴의 마무리: 취소를 에러 응답으로 바꾸지 않고 다시 throw해 후속 노드를 즉시 중단하고, 마지막 토큰 flush/이력 저장/후속 이벤트를 모두 생략. finally에서 리스너를 정리해 누수 방지

병렬 트랙의 공유 상태 경쟁 조건

상황: 답변/카드/후속 질문 트랙을 병렬 실행했고, 모든 트랙이 같은 LangGraph state와 요청 컨텍스트를 공유

  • 헤더/state 여러 곳에서 따로 해석하던 응답 언어를 요청 진입 시 한 번만 확정해 트랙마다 언어가 달라지는 문제 제거

실행 계획 기반 개선

EXPLAIN ANALYZE로 실제 병목 노드를 확인한 뒤 안티패턴별로 고쳤습니다.

1) 스칼라 서브쿼리 → JOIN 1회

-- 기존: 행마다 메타 테이블을 3번 조회
SELECT (SELECT album_id  FROM music_meta WHERE idx = e.word_idx) AS album_id,
       (SELECT song_id   FROM music_meta WHERE idx = e.word_idx) AS song_id,
       (SELECT singer_id FROM music_meta WHERE idx = e.word_idx) AS artist_id, ...

-- 개선: 한 번의 JOIN으로 세 컬럼을 함께 조회
SELECT DISTINCT m.album_id, m.song_id, m.singer_id, ...
FROM work w
JOIN entity_dict e ON e.work_idx   = w.work_idx
JOIN music_meta  m ON m.idx        = e.word_idx
JOIN tts_dict    t ON t.entity_idx = e.entity_idx
JOIN stt_dict    s ON s.entity_idx = e.entity_idx
  • 이중 조회용 인라인 뷰, 내부 ORDER BY, 이중 GROUP BY를 제거하고 DISTINCT 한 번으로 정리
  • 암묵적 조인을 명시적 JOIN으로 바꿔 조인 조건과 필터 조건을 분리

2) 날짜 함수 조건 → 반개구간 범위 조건

-- 기존: 컬럼을 가공해 인덱스 사용 불가
WHERE to_char(w.complete_date, 'YYYYMMDD') = :target_date

WHERE w.complete_date >= :target_date::date
  AND w.complete_date <  :target_date::date + INTERVAL '1 day'

핵심 판단: ORM의 자동 동작에 기대지 않고 실제 쿼리 실행 시점을 확인한 뒤, 저장과 조회의 순서를 코드 흐름으로 통제한다.

권한 일괄 처리의 반복 쿼리 개선

상황: 수백~수천 명의 상담원 권한을 테넌트/파트/메뉴 단위로 일괄 승인

원인 분석

  • 반복문 안에서 엔티티를 수정한 뒤 다음 findBy 조회를 실행하면, 영속성 컨텍스트의 변경 내용이 조회 결과에 반영되도록 JPA가 조회 직전에 auto-flush 실행
  • 그 결과 루프 1회마다 의도하지 않은 UPDATE와 SELECT가 함께 나가 2N회 쿼리 발생
  • SQL 로그와 Hibernate statistics로 쿼리가 실제로 언제 나가는지 확인해 원인 특정

개선

  • 존재 여부만 필요한 조회를 exists 방식으로 변경
  • 신규 생성 대상과 수정 대상을 먼저 분리
  • 반복문 안에서는 변경만 모으고 마지막에 일괄 저장해 루프 중 flush가 일어나지 않게 함
  • Hibernate statistics로 개선 전후 쿼리 수 비교

결과: 처리 건수에 비례해 2N회 발생하던 쿼리를 N+1회로 줄여 반복 쿼리 수를 약 절반으로 감소

운영 관측성과 배포 표준화

  • OpenSearch 쿼리 템플릿과 인덱스 매핑 표준화
  • 역할별 접근 권한(RBAC)과 설정 변경 이력(Audit Log) 적용
  • Jenkins 기반 CI/CD 자동화
  • 운영자가 로그와 변경 이력을 직접 확인할 수 있는 구조 마련
