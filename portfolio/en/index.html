Values that could mislead the LLM should be removed from its input, not merely forbidden by prompt rules.

Separating Interpretation from Execution

I split each turn into four stages connected exclusively through explicit contracts—JSON slots and state—instead of free-form text.

Stage Responsibility Explicitly excluded
Input Understanding (one LLM call) Extract and normalize intents and entities; mark references to previous values. Final product selection and policy decisions.
Router (pure function) Choose the execution path using only structured commands and stored state. Reinterpreting the customer's raw utterance.
Flow Engine / Inquiry Runtime Run subscription, modification, cancellation, and recommendation flows; execute lookup tools in parallel. Unconstrained policy decisions by the AI.
Response Composer Assemble validated text, cards, and buttons. Overriding system decisions.
  • Contracts before implementation: Defined contracts and tests for eight command types, conversation state, button tokens, tool specifications, and UI commands before connecting the runtime. From then on, implementation meant fulfilling those contracts, so responsibilities never bled across stages.
  • Pure-function routing: Kept LLM and I/O calls out of the Router so identical commands and states always produce the same route. Routing could then be unit-tested deterministically.
  • Shadow testing before migration: Logged the new Router and fast-path decisions without using them in responses. Compared their decisions against the existing path before migrating all turns to the new engine.
  • Preventing stale button replay: Encrypted button and form tokens using AES-GCM and bound session, business operation, and stage identifiers as additional authenticated data (AAD). Expired-stage and cross-session tokens were rejected during decryption, closing server-side paths to duplicate subscription or cancellation actions.
  • Bypassing the LLM for deterministic UI events: Treated fixed strings sent by buttons and chips as part of the UI contract. Only exact matches took the fast path, eliminating one LLM call and removing classification variability.

The Backend Should Not Reinterpret Customer Utterances

Problem

Even when the LLM correctly normalized “Tokyo” to Japan or “one week” to seven days, backend post-processing removed the values because the literal strings did not appear in the original utterance. Customers then had to repeat information they had already provided. Although interpretation was delegated to the LLM, the backend effectively interpreted the same text a second time. Every new expression required more regular expressions and vocabulary lists, leaving inevitable gaps.

Solution

  • Redefined the responsibility boundary: Exposed the evidence needed for decisions as structured LLM output fields; the backend reads those fields rather than inspecting the original text.
    • Request type: action, question, issue, or statement. For example, “How much would it cost to subscribe?” does not initiate a subscription flow.
    • Other fields: duration extensions, fields to modify, schedule shifts in days, product conditions (type, tier, plan), and excluded products.
  • Removed raw-text pattern matching based on verb lists, sentence endings, and city-to-country dictionaries.
  • Do not compensate for LLM errors with more post-processing: Added contrastive examples to prompts, tested whether example JSON parsed according to the contracts, and added real-LLM E2E cases.
  • Documented this as a team engineering principle: update contracts, prompts, and tests together as part of the same change.

From Production Log Analysis to Multi-Turn Architecture Redesign

1. Classifying production logs by root cause

I classified the production logs under review into 12 root-cause categories.

  • Repeated companion-number prompts: Customers traveling alone entered their own number into an optional companion-number field. Invalid values were automatically populated into the reopened form, causing the same failure repeatedly, and the system had no command for proceeding without a number.
    • Fix: Clear the invalid slot; rewrite the error message to lead with the reason; add a “Subscribe without companion numbers” button; represent “no numbers” explicitly as an empty list in the contract.
  • Repeated clarification buttons: Buttons sent strings the agent could not interpret, triggering the same clarification prompt again. Updated the buttons to send self-contained commands and fall back to a fixed service menu if a button response still led to clarification.
  • Responses inconsistent with workflow state: “I want to cancel” could generate a workflow-aborted message even when no operation was in progress. Made workflow-specific confirmation/cancellation commands valid only when the state contains a pending action they can address.
  • Conversation history misclassified as current intent: Suggestions in previous bot responses and stored history frequently affected the intent detected for the next turn.
    • A line-selection button label left in the conversation history was mistakenly extracted as the phone number to look up now.
    • Incorrect bot responses were saved as history, fed back into subsequent turns, and reinforced the original error.

The recurring pattern was cross-turn contamination: values from earlier turns were being mixed into the current request. Individual patches would not eliminate the underlying problem.

2. Root-cause analysis

I rejected two apparent quick fixes: using regular expressions to check whether each extracted value appeared verbatim in the current utterance, and adding more prohibitions to the prompt. In the observed failures, specific field instructions had overridden general exclusion rules.

The architectural conclusion was straightforward: if the LLM must not use a value, do not include that value in its input.

3. Carrying context through structured state, not raw conversation history

Restricting LLM input to the current utterance and value-free state

  • Removed raw history, rewritten requests from an upstream agent, previously extracted values, and bot messages.
  • Passed only the active operation, pending question, and names of populated slots in state—never their values.

Conditional carryover handled by backend code

  • Retrieved values only from the last five turns of structured interpretations stored by the backend.
  • Explicit carryover matrix: Carried over destination, duration, party size, and product fields only as defined groups. Values from the current turn took precedence; undeclared fields never carried over.
  • Explicit references: For “that product,” “there,” or “the same duration,” the LLM emitted a reference marker; the backend resolved the actual value.
  • Explicit resets: Utterances such as “I don't know the duration yet” set a dedicated field instructing the backend to discard the prior value.
  • Excluded clarification and refusal turns from stored carryover context, preventing, for example, “What's the weather in Seoul?” from contaminating a later “Recommend a roaming plan.”

Replacing raw-history dependencies with buttons and state

Without raw history, utterances such as “yes,” “the second one,” and “what about Vietnam?” cannot always be interpreted on their own. Instead of reintroducing history, I redesigned how the bot asks questions.

  • Use buttons for confirmations and suggestions: A plain “yes” only makes sense if the previous bot question is available. The bot now presents such choices as buttons/chips that emit self-contained commands, preserving the choice as a structured event instead of free text.
  • Track presented options: Store only product-list counts and labels in state; backend code resolves the actual product for “the second one.”
  • Resolve elliptical follow-ups: For “what about Vietnam?”, pass only the type of lookup actually answered in the previous turn.

As a result, the LLM extracts intents and entities from the current utterance and value-free state, while the backend handles continuity entirely through structured history. This extends the slot-based entity carryover architecture I had built for the Weather Agent to include roaming workflow steps, confirmations, and clarification states.

  • Only one elliptical-question case regressed under isolation; I fixed it by passing the prior lookup type in state. I also fixed an existing bug that split a recommended destination string into individual characters.

Verifying AI Responses Against System Decisions

Fact-level response validation

  • Instead of parsing generated response sentences with regular expressions, required the response LLM to emit a structured list of the claims it made: country support, promotion status, subscription status, and start-date restrictions.
  • Compared claims against authoritative system decisions. When a contradiction occurred, removed or replaced the offending sentence and any inconsistent product cards with system-approved wording.
  • Generated product cards from lookup results in code, not LLM output, keeping displayed cards consistent with their source data.

Three-stage structured-content leakage recovery

Strict structured output enforces the top-level JSON schema but cannot prevent JSON snippets or code blocks from appearing inside a text field.

Stage Action Acceptance condition
1. Extract Keep only valid response text preceding the leaked structure. Valid response text remains.
2. Rewrite Call an LLM to fix formatting only. Rewritten length is between 0.5× and 1.5× the original.
3. Truncate Cut the output immediately before the leaked structure. Last resort.
  • Revalidated the recovered text and its corresponding list of claims against system decisions, preventing recovery from bypassing factual checks.
  • Kept raw downstream-system responses (including internal error codes) in logs only and generated customer-facing messages from structured values. Tests verified that internal messages could not leak to customers.
  • Encoded interpretation-stage inputs as JSON to prevent spoofed delimiters within customer utterances, and blocked requests for JSON/code-formatted outputs with input guardrails.

Production Reliability

Graceful shutdown without losing streams during deployments

The /talk endpoint returned its initial response before continuing to stream through Event Hubs in the background. On deployment SIGTERM, these background tasks were not tracked, so streams could stop silently.

  • Registered background tasks with strong references to prevent premature garbage collection, and logged unhandled exceptions.
  • During FastAPI lifespan shutdown, drained in-flight tasks for 20 seconds; on timeout, propagated cancellation only once per task. This prevented a second cancellation from interrupting cleanup inside a generator's finally block.
  • Kept shared HTTP sessions open until in-flight cleanup finished, but blocked new sessions from being created.
  • Explicit shutdown budget: Azure Container Apps grace period (30 s) > drain (20 s) + cancellation confirmation (5 s), allowing cleanup before SIGKILL.
  • Separated the timeout for publishing streaming chunks (5 s) from that for terminal events (60 s). Event Hubs outages were classified as stream failures; payload rejection was handled without terminating the stream.
  • Locked down shutdown and cancellation scenarios with unit tests.

Deterministic Event Hubs partition routing

Partition selection originally used Python's hash(transaction_id). Python randomizes string-hash seeds across processes (PYTHONHASHSEED), so the same transaction could be routed to different partitions by different workers or pods.

  • Replaced it with deterministic SHA-256 hashing, ensuring the same transaction always maps to the same partition regardless of process.
  • Moved the partition count from a hardcoded constant to an environment variable consistent with the deployment manifest, preventing divergence from infrastructure configuration.

Measurement and Reproduction Tools

  • Production-log replay: Parsed production requests stored in varied formats (JSON, Python dict representations, truncated data, and double-wrapped records). When traces were unavailable, reconstructed conversations from state history to reproduce production failures locally.
  • Turn-level observability: Logged LLM and tool call counts, state size, and first-emission timestamps as trace fields; aggregated them with Application Insights analysis scripts.
  • Stronger E2E assertions: Checked workflow state (including whether a flow had started) and forbidden LLM output fields in addition to response text. Found a test-evaluator defect that incorrectly counted system errors as PASS and fixed it so system errors always count as FAIL.
  • Version comparison tool: Ran the same cases in parallel against multiple configurations (commit/model/deployment) and compared turn outcomes, token usage, latency, and prompt-cache hit rates across 3,896 turns.
    • Used it to measure a prompt-reordering experiment (moving static catalogs earlier and the current time into a user message): interpretation-stage cache hit rate 94.2% → 94.8% and response-stage rate 62.1% → 62.3%. Quantified the small gains and adjusted follow-up priorities accordingly.

  • Replaced an LLM-intent-driven implementation with a contract-based, staged conversation engine after shadow testing.
  • Classified production issues by root cause, identified recurring cross-turn contamination, and eliminated the architectural dependency on raw conversation history.
  • Passed all 294 cases in two core regression suites and 494 cases across four multi-turn suites.
  • In a three-way comparison on the same 2,116 turns, the combined migration and redesign cut estimated cost by 73.5% ($56.91 → $15.06) and raised the pass rate 90.0% → 94.8% and the multi-turn pass rate 85.9% → 95.8%.

  • Improved deployment and messaging resilience with graceful shutdown and deterministic partition hashing.

If the LLM should not see a value, remove it from the input instead of adding prompt prohibitions. If a conversation requires raw history to interpret a choice, redesign the interaction so the choice is structured from the start. Once interpretation is delegated to the LLM, the backend should consume explicit evidence through a contract—not guess at the original wording again.

Redesigning Temporal Meaning as Independent Dimensions

Schema evolution: moving computation out of the LLM

Version Design Limitation discovered
v0 LLM read the current time and computed offsets such as hoursAhead and daysAhead. Timezone/date arithmetic errors propagated directly to output; results varied between calls.
v1 Removed the current time from LLM input and fixed the server reference time to UTC. The LLM still calculated numeric offsets such as “how many days ahead.”
v2 Separated fields that preserve the original expression: relative time, specific time, relative days, specific date, and weekday. Encoded direction and duration in one duration value (negative meant past).
v3 Began separating direction from duration, added weeks, represented times of day as ranges, and moved weekday/weekend calculations to the backend. A sign alone could not express both direction and boundary inclusion.
v4 Enforced one responsibility per field: five independent dimensions, typed processing stages, and separate policy files. The LLM still inferred AM/PM for ambiguous times.
v4.1 Moved AM/PM resolution to backend code, after the sparse-output change exposed inconsistent LLM inference. — (current version)

Key change from v0 to v2: The queried location's timezone was not known until after an external API call, yet the original design required the LLM to calculate dates before that response arrived. I removed the current time from the prompt, limited the LLM to extracting the user's original temporal expressions, and moved offset calculations to backend code using UTC timestamps after retrieving the location's tzOffset.

Turning point: hourly requests that erased the requested time range

To handle phrases like mỗi tiếng (“every hour”) and từng khung giờ (“by time slot”), a prompt rule had been added: for hourly expressions, set delta=5, relativeHours=0, and all remaining time fields to null.

  • từng khung giờ tối nay (“hourly tonight”) → the rule discarded “tonight” and requested five hours from the current time.
  • Even if the model preserved timeOfDay=eve, the simultaneous relativeHours=0 took precedence in the resolver, again yielding a range starting now.
  • Removing the rule made Đà Lạt mỗi tiếng produce all-null fields, changing a list response into a single response.

Root cause: This was a schema-design problem, not a prompt-priority problem.

  • The single delta field carried three different responsibilities: range length, list-versus-single-response selection, and hour-versus-day granularity.
  • delta=5 could mean “five hours explicitly requested,” “the product's default of five items,” or simply “an hourly request.”
  • timeOfDay already represented a range with a start, end, and length; the hourly rule created a second, conflicting range.

Rejected alternative: Split delta into hourlyDelta and dailyDelta. This would remove unit ambiguity but leave range length and response granularity entangled.

Solution: Single responsibility per entity field

  • Separated range length (delta), unit (deltaUnit), reference-boundary relation (rangeRelation), and response granularity (requestedGranularity).
  • Hourly requests indicate presentation granularity only; they neither construct a new time range nor erase other temporal fields.
  • Kept unspecified defaults and sentinels (such as relativeHours=0 meaning “now”) out of the extracted entity. Backend policy selects default windows and list behavior.

v4: Five semantic dimensions

Dimension Fields Question answered
Date selection specificDate, relativeDays, specificWeekday, weekPart (+ relativeWeeks modifier) Which day?
Time of day specificHour, meridiem, timeOfDay, relativeHours When during the day?
Explicit duration delta (always positive), deltaUnit (hour/day) How many forecast points?

  • “Three days from now” (relativeDays=3, a point in time) and “for the next three days” (delta=3, after, a continuous interval) use separate fields.
  • Ambiguous quantities such as “a few days” or Vietnamese vài ngày are not forced into arbitrary numbers.

v4.1: Resolving AM/PM in backend code

For expressions such as 6 giờ đêm nay (“6 tonight”), the LLM inconsistently inferred meridiem using a time-of-day word without an explicit AM/PM marker. The original schema made specificHour and timeOfDay mutually exclusive, forcing the LLM to infer meridiem from information it was instructed to discard.

  • Allowed specificHour and timeOfDay to coexist and preserved both the numeric hour and any time-of-day expression.
  • Unless the user explicitly says “8 giờ tối” or “7 pm,” the LLM returns meridiem=null; the backend resolves meridiem from the (time-of-day, hour) pair.
  • Defined dawn/morning as AM and afternoon/evening as PM in policy. For categories crossing midnight or noon, such as night and lunch, resolved by hour (night 6–11 → PM; night 12–5 → AM).

Separating Computation into Typed Pipeline Stages

RawTimeEntity → ForecastQueryPlan → CanonicalRange → ResolvedRange → PresentationPlan

Each stage returns a distinct type. Later stages do not reinterpret the semantics established by earlier ones.

Stage Responsibility
RawTimeEntity — Parse input Validate LLM output types and formats, round-trip-check real calendar dates (reject impossible dates such as February 30), distinguish 0 from missing values, validate dependent fields (deltaUnit requires delta), and support legacy outputs.
ForecastQueryPlan — Resolve meaning Use shared resolveByPriority logic and configurable policy to select date, time, duration, and output granularity; record the decision's source in traces.
CanonicalRange — Calculate range Use the queried city's local timezone to calculate overnight intervals (21:00–05:00) and week boundaries; if the current time falls inside an interval, return only the remaining portion.
ResolvedRange — Enforce forecast limits Reject fully past ranges, trim partially past ranges to the present with an explanation, and if only the end of a range exceeds the forecast horizon, cap it at the limit (96 hourly or 15 daily points).
PresentationPlan — Plan output Derive the response type and card range from the same resolved data; limit card cells to the available forecast horizon.
  • Isolated temporal policies, forecast limits, and card presentation in separate policy files, so product changes such as raising the default from five to seven hourly items no longer required changes to interpretation logic.
  • Recorded a source for every decision, making it possible to tell from logs whether an incorrect range originated in LLM extraction or backend calculation.
  • Decomposed an approximately 500-line resolver into stage-specific modules and rewrote tests around the contracts of each stage.

Modeling Multilingual Time Expressions Consistently

  • The Vietnamese tới (“upcoming”) implies different start points by unit: trong 3 ngày tới (“over the next three days”) starts tomorrow, while trong 5 giờ tới (“over the next five hours”) starts now.
  • Modeled this as a unit-semantic distinction instead of a language-specific string exception: days are discrete calendar blocks; hours use a continuous rolling window.
  • Separated point offsets (10 giờ nữa = a single point ten hours later) from durations (10 giờ tới = the next ten hours).
  • Treated Vietnamese typed without diacritics (toi, sap toi) as a future marker only in temporal-range contexts.

Multi-Turn Context and Location Normalization

  • Searched earlier turns backward from the most recent for location, time, and weather metrics. Carried over temporal values as entire blocks, not individual fields, to avoid merging incompatible time expressions from different turns.
  • Combined “What's the weather next week?” followed by “What about Monday?” into next Monday, but not when the current turn supplied a different date expression.
  • Inherited a metric only when omitted; treated all as an explicit reset, so “Will it rain?” followed by “How's the weather?” would not retain a precipitation-only filter.
  • Removed raw conversation history from entity-extraction inputs and assigned all multi-turn carryover to backend code. This later became the foundation for the roaming agent's multi-turn isolation design.
  • Kept English lookup names (Ho Chi Minh City) separate from native names for display and speech (Hồ Chí Minh), avoided transliterating foreign cities, and did not invent corrections for unknown locations.

Correctness Across Disconnects and Concurrent Execution

Cancelling the entire call chain when a user disconnects

Problem: Even when users disconnected before receiving an answer, LangGraph execution, LLM streaming, and Knowledge API calls continued until completion. Questions and answers never delivered to the user were still written to multi-turn history, contaminating later conversations and consuming tokens and connections without a recipient.

Design: Propagate one client-disconnect signal across the full request call chain.

  • Implemented a handler connecting the SSE response's close event to a request-scoped AbortController (signal, isCancelled, cleanup).
  • Guarded normal close events after a completed write (writableEnded) so they were not mistaken for cancellation.
  • Passed the same signal through graph.invoke, shared model-call adapters, and Knowledge API streams, applying cancellation across all LLM calls without changing each individual agent.
  • Adapted to each provider: GPT SDK signal, Gemini config.abortSignal, and Gemma fetch signal.

Distinguishing timeouts from user cancellation

  • Combined provider timeout signals and client signals with AbortSignal.any, stopping on whichever fired first.
  • Since both cases surfaced as AbortError, inspected the client signal's aborted state to determine the cause.
  • Logged client cancellations as cancelled at info level and provider timeouts as timeout at warn level, keeping user departures out of LLM failure metrics.

Ending a disconnected turn: Rethrew the cancellation instead of converting it into an error response. This stopped downstream nodes immediately and skipped final-token flushes, history writes, and follow-up events. Cleaned up listeners in finally to avoid leaks.

Race conditions caused by shared state across parallel tracks

Situation: Answer, card, and follow-up-question tracks ran concurrently and shared the same LangGraph state and request context.

Finding

  • The answer track was supposed to run without history to prevent locations and times from other turns leaking in; it accomplished this by directly clearing the history on a shared object.
  • The follow-up-question track needed that history, so its result depended on the execution order across await points—it sometimes saw history and sometimes did not.
  • Single-threaded Node.js can still exhibit race conditions when asynchronous operations interleave around await and mutate shared objects.

Fix

  • Reproduced the race and located every shared-state mutation.
  • Passed history requirements as a per-call argument (useHistory) instead of mutating shared state, which became read-only.
  • Resolved response language once at request entry rather than independently from headers and state inside different tracks, preventing inconsistent languages across outputs.

Outcomes and Lessons Learned

  • Redesigned temporal entities into five independent semantic dimensions and a five-stage typed pipeline, recording decision provenance so incorrect ranges could be traced from logs.
  • Reduced LLM input by up to 99.5%, extraction output tokens by 55.8%, and mean extraction latency by 15% (573 ms).
  • Cut external API latency by up to 84.2% and TTFT by 40.7%, tracing and fixing buffering issues all the way through the infrastructure layer.
  • Eliminated history contamination after client disconnection and shared-state race conditions across parallel tracks.

Overloading a single field with multiple meanings forces prompt rules and exception handling to grow together. Independent semantic fields, LLM-only extraction, and backend-owned calculation, validation, and consistency produce more reproducible behavior. Effective optimization also means measuring not only the improvement, but the limit of that approach—so the next engineering investment is informed by evidence.

  • The same inefficient SQL patterns appeared across seven queries.
Anti-pattern Original approach Impact
Row-by-row scalar subqueries Queried the same metadata table three times, once for each column. Three repeated lookups per result row.
Duplicate lookups with the same predicate Queried a job ID and then joined the same table again under the same condition. Repeated scans of the same table.
Redundant sorting/grouping Nested ORDER BY clauses and duplicate GROUP BY clauses that did not affect the result. Unnecessary sorting and deduplication.
Function applied to date column to_char(complete_date, 'YYYYMMDD') = '20250806' Prevented direct use of the date index and caused a full scan.

Execution-Plan-Driven Optimization

I used EXPLAIN ANALYZE to identify the actual expensive plan nodes before addressing each pattern.

1. Scalar subqueries → One JOIN

-- Before: query the metadata table three times per row
SELECT (SELECT album_id  FROM music_meta WHERE idx = e.word_idx) AS album_id,
       (SELECT song_id   FROM music_meta WHERE idx = e.word_idx) AS song_id,
       (SELECT singer_id FROM music_meta WHERE idx = e.word_idx) AS artist_id, ...

-- After: retrieve all three columns with one JOIN
SELECT DISTINCT m.album_id, m.song_id, m.singer_id, ...
FROM work w
JOIN entity_dict e ON e.work_idx   = w.work_idx
JOIN music_meta  m ON m.idx        = e.word_idx
JOIN tts_dict    t ON t.entity_idx = e.entity_idx
JOIN stt_dict    s ON s.entity_idx = e.entity_idx
  • Removed an inline view used for duplicate lookups, unnecessary inner ORDER BY clauses, and redundant grouping; replaced them with one DISTINCT where appropriate.
  • Converted implicit joins into explicit JOIN syntax to separate join conditions from filtering predicates.

2. Date formatting predicate → Half-open range

-- Before: transform the indexed column
WHERE to_char(w.complete_date, 'YYYYMMDD') = :target_date

-- After: compare the raw column over [start of day, next day)
WHERE w.complete_date >= :target_date::date
  AND w.complete_date <  :target_date::date + INTERVAL '1 day'
  • Designed composite indexes around date conditions and frequently used filters, enabling a move from sequential scans toward index scans where semantics permitted.

3. Repeated subqueries → Calculate once in a CTE

  • TV utterance dictionaries were generated by attaching different templates—such as “play ,” “show ~,” and “ on YouTube”—to the same content via UNION ALL.
  • Calculated the latest job date within the period and the target content once in a CTE; each branch then performed only its string concatenation.

Verifying Result Equivalence

  • Executed the original and optimized queries against three days of real production data (August 6–8, 2025) and stored their results in temporary tables.
  • Compared row counts and complete row-level sets; deployed only after 100% equivalence across all seven queries was confirmed.

An optimization rejected for correctness: retaining to_char

  • One TV date-range query first selected the latest job date in the range, then joined all jobs completed on that date.
  • Because the completion column was timestamptz, replacing the date-formatted comparison with an exact timestamp match returned only rows completed at the same time, omitting other jobs completed on the same calendar day.
  • The new plan used an index and ran faster, but did not preserve business semantics. I kept to_char for that case and improved performance through reduced subquery duplication and simpler joins instead.

Reducing Repeated Queries During Bulk Permission Updates

Context: Bulk approval of permissions for hundreds or thousands of call-center agents, scoped by tenant, department, and menu.

Root-cause analysis

  • When code modified an entity inside a loop and then executed another findBy query, JPA performed an automatic flush before the query so the query would reflect changes in the persistence context.
  • Each iteration therefore issued an unintended UPDATE alongside a SELECT, producing approximately 2N queries.
  • Confirmed precisely when queries executed using SQL logs and Hibernate statistics.

Fix

  • Replaced full lookups with existence checks where only existence mattered.
  • Separated records to create from records to update before processing.
  • Collected modifications inside the loop and performed the bulk save at the end, preventing intermediate flushes.
  • Compared query counts before and after using Hibernate statistics.

Result: Reduced query count from approximately 2N to N+1, nearly halving the number of queries as the batch size increased.
